# 개발 및 릴리스 운영 규칙

## 브랜치 / Pull Request

- `main`: 검토·승인된 변경만 병합할 기준선. 현재는 운영본과 일치한다고 가정하지 않음.
- `feat/<topic>`, `fix/<topic>`, `chore/<topic>`: 작업별 브랜치 사용.
- PR 설명에 목적, 변경 파일, 영향 받는 기능, 테스트 실측, 저장 데이터 영향, 복구 방법을 기록.
- 게임 패치와 UI·BGM·에셋 교체를 임의로 통합하지 않으며, 기존 기능 보존을 비교 검증.
- 운영 버전 번호(Cloudflare Worker 숫자)와 내부 게임 빌드 번호를 구분.

## 실행·배포 경계

- GitHub push, Issue, PR 생성·병합만으로 Cloudflare Worker 또는 도메인이 업데이트되지 않음.
- CI/CD, GitHub Actions, 자동 Cloudflare 배포를 설정하지 않음. 필요한 검증은 기존 수동/로컬 검사와 배포 후 readback 우선.
- 실제 운영 배포는 승인된 범위에서 별도 수행하고 배포 ID, Worker 버전, URL, healthz, 롤백 후보를 기록.
- 운영 사이트의 저장 키와 `localStorage`를 임의 변경·삭제하거나 호환성을 추정하지 않음. 이전 저장 읽기 fallback 유지 여부 확인.
- 배포 전 PC와 Android 실기기: 이동·채굴·로프, 월드 전환, 음악, 가로/세로, 멀티터치, 기존 세이브 복원을 검증.
- 원본 음원/폰트/이미지/에셋은 사용 권한을 확인한 뒤 업로드. 개인 인증정보, API 키, 토큰, .env 파일을 커밋하지 않음.

## 작업 상태

- 설계/후보, 코드 반영, 로컬 QA, PR 병합, 운영 배포, 배포 후 검증은 서로 다른 단계.
- 테스트 미수행 항목은 PASS 처리하지 않고 근거와 제한을 기록.
- 기존 이관 자료와 Cloudflare 운영 상태가 충돌하면 이를 기록하고 새로운 운영 사실을 독립 재조회.

## 소스 디렉터리 원칙

소스 이관 검증 전까지 빈 `src/` 또는 `public/` 경로를 가상의 구현처럼 만들지 않음. 실제 소스가 확보되면 게임 본체, 운영 Worker, 타이틀 브리지, 에셋 및 테스트의 경계를 구분해 단계적으로 추가.
